# Корректность торгов Friends Auction: независимая проверка

Дата: 24 ноября 2026 года. Объект: `v1.1.0`, commit `45ccee95610328be1bdb23e5ae81325b6540f4d6`. Исходники не изменялись. Производственные данные, фотографии, конфигурация, бот и действующий сервис не использовались.

## Вывод

Базовая запись ставок устроена разумно для небольшого аукциона на одном сервере: `BEGIN IMMEDIATE`, повторная проверка допуска после получения блокировки, точное сравнение ожидаемой цены, повторная проверка времени непосредственно перед вставкой, атомарные подписки и события. Изолированные дополнительные проверки подтвердили запрет ставки после отзыва допуска во время ожидания блокировки и после окончания торгов во время того же ожидания. Ранжирование кандидатов берёт максимум каждого участника, последовательно исключает отказы и сохраняет исходные ставки.

Обнаружены три конкретных нарушения/ограничения согласованности. Одно касается завершения срока хранения, два — подтверждения изменённых условий и уведомления следующего кандидата. Ни одно не означает анонимный обход авторизации или возможность произвольно менять чужие ставки.

| ID     | Приоритет                | Статус                                                         | Результат                                                                                                                         |
| ------ | ------------------------ | -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| BID-01 | P1 к окончанию хранения  | Воспроизведено с управляемым порядком конкурентного исполнения | Начавшийся до истечения срока запрос может записать имя и заявку после успешной окончательной очистки worker.                     |
| BID-02 | P2 до завершения торгов  | Воспроизведено через API                                       | Первая ставка по старой карточке принимается после изменения названия/описания/состояния, если ожидаемая цена по-прежнему `null`. |
| BID-03 | P2 до выдачи результатов | Воспроизведено с offline send-adapter                          | Параллельный отказ от следующего кандидата не отменяет уже проверенное уведомление этому кандидату.                               |

P1 здесь означает нарушение заявленной границы удаления, которое следует исправить до 1 февраля 2027 года; это не доказательство немедленной критической эксплуатации.

## BID-01: запись заявки после окончательной очистки

**Места.** [`throttle`, app.py:281–284](https://github.com/PaVeLlLlLX/friends-auction/blob/45ccee95610328be1bdb23e5ae81325b6540f4d6/auction/app.py#L281-L284) проверяет срок один раз в начале запроса. [`current_user`, app.py:336–361](https://github.com/PaVeLlLlLX/friends-auction/blob/45ccee95610328be1bdb23e5ae81325b6540f4d6/auction/app.py#L336-L361) затем может создать/обновить аккаунт; [`application`, app.py:551–581](https://github.com/PaVeLlLlLX/friends-auction/blob/45ccee95610328be1bdb23e5ae81325b6540f4d6/auction/app.py#L551-L581) сохраняет имена без повторной проверки срока. [`tick`, worker.py:132–142](https://github.com/PaVeLlLlLX/friends-auction/blob/45ccee95610328be1bdb23e5ae81325b6540f4d6/auction/worker.py#L132-L142) удаляет таблицы и файлы, возвращает `True`; [`main`, worker.py:258–260](https://github.com/PaVeLlLlLX/friends-auction/blob/45ccee95610328be1bdb23e5ae81325b6540f4d6/auction/worker.py#L258-L260) прекращает работу после этой очистки.

**Предпосылки.** Подписанный Telegram-пользователь начинает запрос до границы хранения. Обработка продолжается достаточно долго, чтобы очистка завершилась раньше записи. Допуск к торгам не требуется: подача заявки разрешена аутентифицированному пользователю. В реальной конфигурации граница торгов уже прошла, но `application` не ограничивается датой окончания торгов.

**Выполненный тест.** Дополнительный тестовый `before_request` установлен после настоящего `throttle`: он ставит поток заявки на барьер после проверки срока, но до обработчика. Это моделирование допустимого порядка исполнения, а не естественная задержка найденного production-обработчика. Управляемые часы переведены за искусственную границу `DELETE_AFTER`; реальный `tick` в другом потоке очистил БД, вернул `True`, таблица пользователей стала пустой. Затем запрос разблокирован. Он создал нового пользователя и сохранил заявку.

Фактический результат:

```json
{
  "worker_finished": true,
  "users_after_cleanup_before_resume": 0,
  "resumed_application_http": 200,
  "users_written_after_expiry": 1,
  "persisted_status": "pending",
  "persisted_private_name": "Test"
}
```

Это подтверждает некорректность жизненного цикла при выбранном порядке исполнения. Частота такого порядка без искусственного барьера и возможность удалённо управлять точным моментом отдельно не измерялись. Злоумышленная временная атака не заявляется.

**Последствие.** Имена/ID/заявка могут остаться в настроенной БД после финальной очистки. Новые HTTP-запросы получают 410, но недоступность API не удаляет оставшуюся запись. Перезапуск worker способен убрать её; непрерывная гарантия хранения после завершения его цикла этим не обеспечена.

**Минимальное направление исправления.** Согласовать записи и истечение срока одной дисциплиной блокировок: каждый путь, способный записать персональные данные, включая account upsert в GET, должен брать транзакцию записи и проверять срок внутри неё до записи. Финальная очистка использует ту же сериализацию; ожидавший запрос после получения блокировки видит истёкший срок и не создаёт данные. Альтернатива для завершения сервиса — запретить приём новых запросов, дождаться завершения начатых, очистить, затем остановить web/worker; её нужно реализовать и для контейнерного режима. Простого второго `if` вне транзакции недостаточно для общей гарантии. Оценка: 0.5–1.5 дня с проверкой всех account/write-путей, риск регрессии средний.

**Критерий приёмки.** Управляемый конкурентный тест возобновляет `application` и `/api/me` после завершённой очистки; после завершения всех потоков все семь таблиц остаются пустыми, JPEG отсутствуют, обработчик не возвращает успешное подтверждение сохранения данных. Добавить второй порядок, когда начатая запись завершается до очистки: очистка обязана удалить её.

## BID-02: первая ставка не связывается с версией условий лота

**Места.** [`edit_lot`, app.py:907–956](https://github.com/PaVeLlLlLX/friends-auction/blob/45ccee95610328be1bdb23e5ae81325b6540f4d6/auction/app.py#L907-L956) разрешает правку до первой ставки, сериализуя её со ставками. [`bid`, app.py:594–625](https://github.com/PaVeLlLlLX/friends-auction/blob/45ccee95610328be1bdb23e5ae81325b6540f4d6/auction/app.py#L594-L625) проверяет ожидаемую текущую цену, но не версию описания/условий. Пока ставок нет, цена равна `null` независимо от редактирования.

**Выполненный тест.** Одобренный пользователь получает карточку «Бокалы», старт 1000, шаг 100, цена `null`. Организатор меняет название на `Changed item`, описание и состояние на `Broken`, оставляя старт и шаг. Старый запрос участника на первую ставку 1000 с `expected_price:null` получает HTTP 200. Ответ уже содержит новое название. Для воспроизведения достаточно последовательных API-запросов: задержка между получением карточки и отправкой — обычная часть клиентского взаимодействия. В короткой реальной гонке редактирования и ставки результат зависит от порядка захвата блокировки, но выигрыш редактирования допускает этот же сценарий.

**Предпосылки и влияние.** Редактировать может только организатор. Это не атака участника и не обход запрета редактирования после ставки. Однако корректная сериализация БД не подтверждает, что участник видел именно те условия, по которым была принята первая ставка. Polling уменьшает окно, но не закрывает его между отрисовкой/подтверждением/отправкой.

**Исправление.** Добавить возрастающую `revision` или хеш канонических условий лота, включить её в публичную карточку и обязательный payload ставки. Изменять при каждом редактировании полей, влияющих на выбор участника; сравнивать под `BEGIN IMMEDIATE`. При несовпадении — HTTP 409 с предложением повторно подтвердить обновлённую карточку. Сама возможность редактирования до первой ставки сохраняется. Оценка: 3–6 часов с миграцией и клиентским подтверждением, риск средний.

**Критерий приёмки.** Старое подтверждение первой ставки после правки только описания/состояния/названия получает 409 и не создаёт ставку. Повторное подтверждение с новой revision проходит; неизменённая нулевая первая ставка и повышение на несколько шагов продолжают работать. Тест с двумя потоками допускает два порядка: ставка выигрывает — edit 409; edit выигрывает — старая ставка 409.

## BID-03: уведомление уже отказавшему следующему кандидату

**Места.** [`notify_candidate`, app.py:978–1004](https://github.com/PaVeLlLlLX/friends-auction/blob/45ccee95610328be1bdb23e5ae81325b6540f4d6/auction/app.py#L978-L1004) сначала проверяет кандидата и затем вызывает внешний `send_message`. [`admin_lot`, app.py:839–858](https://github.com/PaVeLlLlLX/friends-auction/blob/45ccee95610328be1bdb23e5ae81325b6540f4d6/auction/app.py#L839-L858) может между этими этапами записать следующий отказ. Docstring уведомления честно описывает эту неатомарность.

**Выполненный тест.** Синтетические ставки: ID4 → 0, ID2 → 50, ID3 → 100. После закрытия организатор отказывает ID3, текущий кандидат ID2. Запрос уведомления валидирует ID2. Offline send-adapter до фактической фиксации отправки инициирует независимый административный отказ ID2, выбирающий ID4, затем фиксирует доставку ID2. Запрос уведомления возвращает 200, действующий кандидат уже ID4. Настоящая Telegram-сеть не использовалась; подменена только граница внешнего эффекта.

**Границы.** И уведомление, и отказ требуют прав организатора; возможная причина — параллельные вкладки/устройства или повторные действия самого организатора. Анонимный посетитель вызвать такую смену не может. После фактической отправки уже доставленное сообщение нельзя сделать недоставленным транзакцией SQLite.

**Исправление.** Сериализовать административные операции смены/уведомления кандидата по лоту; хранить выбранную revision и состояние отправки, блокировать смену кандидата пока выбранное сообщение отправляется, затем явно показывать результат. Для отказоустойчивости учитывать состояния `pending/sent/unknown` и не обещать exactly-once при таймауте Telegram. Простое удержание SQLite write lock на внешнем HTTP-запросе решает эту конкретную гонку, но блокирует все записи в единственную БД и потому нежелательно как основной дизайн. Оценка: 0.5–1 дня; риск средний.

**Критерий приёмки.** При одновременных notify/refuse система либо подтверждает уведомление текущему кандидату и задерживает/отклоняет смену, либо фиксирует смену раньше и отклоняет устаревшее уведомление. Интерфейс видит, какому кандидату и в каком состоянии направлено сообщение. При timeout результат показывается как неизвестный; слепая повторная отправка не запускается автоматически.

## Подтверждённые хорошие свойства и границы

- Отзыв допуска учитывается повторно в транзакции ставки. Дополнительный тест удерживал SQLite write lock, наблюдал попытку `BEGIN IMMEDIATE` другого потока, менял статус на rejected и отпускал lock: ставка получила **403, в БД 0 ставок**.
- Дедлайн проверяется после ожидания lock. Во втором таком тесте граница `END` перенесена в прошлое перед освобождением lock: **409, 0 ставок**. Это симуляция границы конфигурацией, а не испытание реальной даты декабря. В штатных тестах также есть управляемые часы на точной границе.
- Максимум берётся по уникальному пользователю. Дополнительный контроль со ставками `(2,0),(3,50),(2,100),(4,150)` дал кандидатов `(4,150),(2,100),(3,50)`; отказы последовательно дали `[2,3]`, `[3]`, `[]`, все **4 ставки сохранились**.
- Ноль обрабатывается через `is not None`, а не truthiness; первая ставка может равняться старту или превышать его на целое число шагов. Последующие суммы строго выше на шаг, собственное лидерство не повышается (`bid`, строки617–625).
- Ставка, включение participation и события watcher/outbid находятся в одной транзакции (`bid`, строки629–652). При откате частичная ставка или подписка не должны сохраняться.
- Delete использует `BEGIN IMMEDIATE`, сравнивает `expected_bid_count`, скрывает лот и отключает подписки в одной транзакции (`delete_lot`, строки887–901). Ставки/фото физически сохраняются; личная история фильтруется по caller ID. Штатные тесты содержат конкуренцию delete/first bid и проверки публичных 404; общий запуск подтверждает основной аудитор.
- Существующие уведомления могут дублироваться при сбое между принятием Telegram и сохранением receipt; это прямо описано в worker/specification. Нельзя объявлять exactly-once.
- `lot_view` делает несколько SELECT без общей read transaction. Полная согласованность нескольких полей одной карточки при одновременной записи не доказана этим аудитом. Защита записи через expected price остаётся самостоятельной. Это вопрос для дополнительного теста, не воспроизведённая новая находка.
- Часы сервера — источник истины. Точность системных часов и фактический стабильный запуск на macOS не измерялись здесь. Проверяется время перед вставкой; отдельного утверждения, что fsync/HTTP-ответ физически завершится до дедлайна, код не устанавливает. В спецификации следует явно понимать принятие как серверную проверку под write lock и записанную временную отметку.

## Первичные внешние источники

1. SQLite, [Transaction](https://www.sqlite.org/lang_transaction.html), прочитано 24.11.2026; страница указывает обновление 18.02.2026. Поддерживает семантику write transaction, `BEGIN IMMEDIATE`, implicit/explicit transaction и busy/commit. `BEGIN IMMEDIATE` сериализует писателей, но не объединяет произвольный последующий autocommit-запрос с завершённой очисткой.
2. SQLite, [Isolation In SQLite](https://www.sqlite.org/isolation.html), прочитано 24.11.2026. Поддерживает отсутствие dirty reads между обычными отдельными соединениями и одиночного писателя. Это не доказательство атомарности внешнего Telegram HTTP-эффекта с локальной БД.
3. Python Software Foundation, [sqlite3 — Python 3.12 documentation](https://docs.python.org/3.12/library/sqlite3.html#transaction-control-via-the-isolation-level-attribute), прочитано 24.11.2026. Поддерживает смысл `isolation_level=None`, явных транзакций, timeout и ограничений использования соединений между потоками. Проверки создают отдельное соединение на запрос, общий connection между потоками не используется.

Не проводились нагрузочные испытания, проверка настоящих Telegram-клиентов, аппаратная проверка iOS/Android и воспроизведение отключения питания/файловой системы. P0 не установлен; отсутствие P0 в этой проверке не является доказательством отсутствия всех дефектов.
